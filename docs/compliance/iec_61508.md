# IEC 61508 SIL 2/3 Functional Safety — Compliance Mapping

See `docs/compliance/README.md` for what this document is and isn't.

IEC 61508 certifies a system to a Safety Integrity Level (SIL 1-4) based
on quantified failure probability targets *and* a prescribed development
process (requirements traceability, structured hazard/risk analysis,
verification independent of the developer, documented tool
qualification, and so on). A SIL is not a property source code can claim
for itself — it's assigned by a functional safety assessment against a
specific safety function, in a specific system, following that process.
This document maps this workspace's engineering practices against the
standard's technical requirement *areas* for software (primarily IEC
61508-3) at the SIL 2/3 band, since that's the part a codebase can
speak to; it does not claim, and cannot grant, a SIL rating.

| Requirement area (IEC 61508-3, SIL 2/3 band) | Status | Where |
|---|---|---|
| Deterministic, bounded-time execution of safety functions | Implemented (software), one documented gap | `docs/deterministic_execution_audit.md` (Phase 11) is the source-level audit this row summarizes: `tpt-t-construction-hydraulic` and `tpt-t-construction-rollover` are fully allocation-free with O(1) or fixed-bound control flow; `tpt-t-construction-safety` is mostly the same except `perception::fuse_detections` and `tracking::TrackManager::update`, which allocate and have no compile-time bound on detection count — recorded there as a known gap with a specific proposed remediation, not silently left out of this document. |
| Defensive programming / avoidance of unbounded recursion, uninitialized memory, undefined behavior | Implemented (software, reviewed) | Every `unsafe` block in this workspace (the `rkyv` archive in `tpt-t-construction-core::messages`, the POD transmutes in `tpt-t-construction-telemetry::record`/`audit`, `tpt-t-construction-hydraulic::realtime`'s raw `libc` calls) carries a `// SAFETY:` comment justifying why it's sound at the point of use — a documented, review-visible practice rather than an aspiration. No recursion in a hot safety loop (the one recursive function in the codebase, `perception::fuse_detections`'s union-find `find`, is bounded by cluster depth and lives in the crate the audit already flags as a gap). |
| Redundancy / diverse monitoring of safety-critical decisions | Implemented (software, partial) | `tpt-t-construction-safety::tmr` (Phase 11) implements the TMR majority-voting decision itself (`vote_exact`, `vote_f32`, disagreement/no-quorum detection). What it does *not* have is three physically independent, diversely-implemented sensor/computation channels feeding it in this workspace — that's the hardware half of "redundant safety monitoring" (todo.md Phase 11), and is Phase 12 scope. |
| Documented, hash-chained audit trail for post-incident analysis and process evidence | Implemented (software) | `tpt-t-construction-telemetry::audit` (Phase 11): an append-only log where each record's hash covers its own fields plus the previous record's hash, so `verify_chain` can detect any alteration, deletion, or reordering after the fact. Its own module docs are explicit that the hash function used (FNV-1a) is non-cryptographic — sufficient against accidental corruption and naive tampering, not against a well-resourced deliberate forgery, which would need a keyed cryptographic MAC and a hardware key store this workspace doesn't have (again a Phase 12 concern). |
| Fault detection and defined failure response (fail-safe state) | Implemented (software) | `tpt-t-construction-core::messages::{Fault, FaultSeverity}` classifies faults by severity; `tpt-t-construction-teleop::fault_handover::handover_response` defines the exact state transition each severity forces (`EmergencyStop` forces the handover FSM to `EmergencyStop` from *any* state — the one universally-legal edge in `safety_fsm.rs`); `tpt-t-construction-rollover::brake::should_apply_brakes` and `tpt-t-construction-safety::response` are themselves fail-toward-safe decision functions (stop, not merely warn, once a margin is exhausted). |
| Requirements traceability (each safety requirement traced to a specific implementation and test) | Implemented (software, informal) | `todo.md`'s phase checklist plus each module's doc comment citing the relevant `spec.txt`/`bridge spec.txt` section is an informal trace from requirement to code. This is *not* the formal, tool-supported traceability matrix a SIL 2/3 assessment expects (e.g. a requirements-management tool cross-referenced to test IDs) — that's a process/tooling investment, not a code change. |
| Independent verification & validation (V&V performed by someone other than the developer) | Blocked on external process | Every line of this workspace, including its tests, was written by the same process (this autonomous session). Independent V&V by construction requires a separate reviewing party — it cannot be self-supplied. |
| Tool qualification (the Rust toolchain itself, as a "software tool" in IEC 61508's sense) | Blocked on external process | IEC 61508-3 requires qualifying the compiler/toolchain used to build a SIL-rated system. `rustc`/`cargo` have no IEC 61508 tool-qualification package as of this writing; obtaining or producing one is outside this workspace's scope. |
| Formal SIL assessment and certificate issuance | Blocked on external process | Performed by an accredited functional-safety assessor (e.g. a TÜV or exida-equivalent body) against a specific, fielded system — not derivable from a repository. |

**Overall status:** the technical practices IEC 61508-3 asks of the
*software itself* — bounded execution, defensive programming,
redundancy logic, fault-safe responses, an auditable record — are
implemented and, where incomplete, explicitly tracked (the
`perception`/`tracking` allocation gap) rather than asserted as done.
The process and third-party requirements (independent V&V, tool
qualification, formal assessment) are named as exactly what they are:
activities this workspace cannot perform on itself.
